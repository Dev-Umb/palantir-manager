## Context

`users` 被业务记录、AI Run、站内通知、审计日志和 RBAC 关联引用。其中部分外键为 `cascadeOnDelete`，物理删除会丢失历史数据；数据库 session 表没有用户外键，删除账号后还需要主动清理会话。

## Goals

- 管理员可以从 RBAC 页面删除单个非受保护账号。
- 删除立即撤销角色与所有数据库会话，使账号不可继续登录。
- 历史业务、AI、通知和审计记录保持存在。
- 并发删除或角色修改不能使系统失去最后一个管理员。

## Non-Goals

- 批量删除、恢复站、账号合并和邮箱复用。
- 删除角色或修改权限模型。
- 清理用户创建的业务记录、附件、AI Run、通知或审计日志。

## Decisions

### 使用软删除而非物理删除

为 `users` 增加 `deleted_at` 并让 `User` 使用 `SoftDeletes`。Laravel 认证查询和隐式路由绑定默认排除软删除用户，因此账号删除后不能重新认证，也不会再次出现在正常用户查询中；外键目标行仍存在，从而保留历史关联。

### 删除动作在事务内完成

删除时锁定目标用户与管理员角色，检查自删和最后管理员规则，先写入包含目标快照与原角色的审计日志，再解除角色、删除该用户数据库会话并软删除用户。事务失败时不得留下部分清理状态。

### 最后管理员保护覆盖删除与角色更新

删除具有 `admin` 角色的用户，或通过角色编辑移除其 `admin` 角色时，均在锁定管理员角色后统计有效管理员。只剩一个时拒绝操作，避免从相邻入口绕过保护。

### UI 只表达服务端判定

RBAC 页面为每个用户返回 `can_delete` 与 `delete_block_reason`。前端禁用受保护用户的删除按钮并显示原因，但服务端始终重复校验，不依赖前端授权。

## Risks and Mitigations

- **并发删除管理员**：事务锁定管理员角色，使所有删除路径串行执行最后管理员检查。
- **已有会话继续使用**：删除 `sessions.user_id` 对应行，并依赖软删除全局作用域使认证提供器无法重新取回用户。
- **历史关系意外丢失**：不执行 `forceDelete`，并以 Feature 测试验证业务记录、AI Run、通知与审计仍存在。
- **邮箱无法复用**：本期明确不支持恢复或邮箱复用，避免两个历史身份共享同一邮箱。
