## Context

客户、联系人和项目都存放在 `object_records`，具体关联位于 JSON `payload`：项目通过 `customer_id` 关联客户，通过 `business_owner_user_id` 指定负责业务员；联系人通过 `customer_id` 归属客户。`ProjectVisibility::scopeRecords()` 已经是通用列表、详情、导出、关系验证和关系选项的统一数据范围入口，但当前客户与联系人没有专用范围，因此业务员能看到全部记录。项目内嵌客户接口只检查角色和记录类型，也缺少记录级可见性校验。

认证使用 `redirect()->intended(route('dashboard'))`。因此默认地址可以按登录用户角色选择，同时保留 Laravel 已保存的 intended 地址。

## Goals and non-goals

Goals:

- 让业务员客户范围由本人负责项目实时推导，不复制归属状态。
- 让本人新建但尚未关联项目的客户在过渡期保持仅本人可见。
- 让联系人、所有客户入口和项目关系选项使用同一数据范围。
- 让未关联客户在项目客户下拉中优先显示。
- 让业务员普通登录默认落在业务项目表。

Non-goals:

- 不新增“客户负责人”字段或客户可见性分类字段。
- 不变更项目负责人、知会人员、经营大盘权限或导航显示。
- 不改变财务、招投标、管理员的客户范围。
- 不迁移、删除或修复既有客户关联。
- 不为客户关联项目建立缓存或异步同步。

## Decisions

### 1. 客户范围实时派生

业务员可见客户满足以下任一条件：

1. 存在至少一个项目，其 `customer_id` 指向该客户且 `business_owner_user_id` 等于当前业务员；
2. 客户 `created_by` 等于当前业务员，并且系统中不存在任何指向该客户的项目。

客户同时关联本人和其他业务员的项目时仍然可见。本人创建的客户一旦只关联到其他业务员负责的项目，就不再因创建人身份继续可见。规则在查询时实时计算，不向客户写入派生归属。

### 2. 联系人继承客户范围

联系人没有独立负责人，也必须关联客户。因此业务员只能查看所属客户可见的联系人。联系人列表、详情、更新、删除和关系选项都复用该规则；不会再创建一套联系人创建人规则。管理员、财务和招投标账号沿用现有行为，其中财务和招投标是否拥有联系人对象权限仍由现有 RBAC 决定。

### 3. 服务端入口完整覆盖

通用业务对象列表、详情选择、搜索、筛选、导出、更新、删除和关联验证继续经过 `ProjectVisibility::scopeRecords()` / `allowsRecord()`。项目内嵌客户管理接口补充同一记录级检查，并对联系人写入同时验证所属客户可见。不可见记录的直接读取返回 404，写入返回 403 或 404，以现有控制器相邻契约为准，且不得泄露记录内容。

### 4. 项目客户选项顺序

仅对来源对象为 `project`、字段为 `customer_id`、目标为 `customer` 的关系选项应用专用排序：

1. 没有关联任何项目的客户；
2. 已有关联项目的客户；
3. 每组按 `created_at` 降序、`id` 稳定排序。

搜索仍在当前用户可见范围内执行。编辑记录当前选择通过既有 `selectedItems` 通道保留，即使它不在前 50 个可用选项中也必须显示。

### 5. 登录默认落点及角色优先级

认证成功后先计算 fallback：仅具有业务角色且不具有管理员、财务或招投标角色的账号使用 `/objects/project`；管理员、财务、招投标及其他账号继续使用经营大盘。随后调用 `redirect()->intended($fallback)`，因此用户主动请求的受保护地址优先于默认落点。

注册后的自动登录保持原经营大盘落点，因为注册默认角色不属于本次已确认的业务员登录场景。

### 6. 本地共享客户演示数据

全链路演示 Seeder 会建立同一客户由不同业务员项目共同关联的矩阵。普通业务员按新规则不能主动选择当前只属于其他业务员项目的客户，因此 Seeder 使用既有管理员账号作为关系校验主体创建项目，完成后仍把 `created_by` 恢复为项目负责人。该调整只影响显式运行的本地演示数据生成，不进入生产请求流程，也不改变演示项目的最终归属。

## Risks and mitigations

- JSON 关联查询在 PostgreSQL 与 SQLite 方言不同：集中封装客户关联表达式，使用现有数据库驱动分支模式，并在 SQLite Feature 测试及生产 PostgreSQL 只读查询计划检查中验证。
- 只收紧列表但遗漏嵌入式接口会造成越权：测试列表、详情、导出、关系搜索、项目内 GET/PUT/联系人接口的 allow/deny 矩阵。
- 关系选项排序可能挤掉当前值：保留独立 selected query，并测试当前值超过选项上限时仍存在。
- 多角色账号默认落点不明确：采用最小改变原则，高权限或跨职能账号继续进入经营大盘，只有纯业务员改变 fallback。

## Migration and rollback

没有数据库迁移或数据回填。回滚只需移除客户/联系人范围分支、内嵌接口记录级检查、项目客户选项专用排序和角色 fallback；客户、联系人、项目、审计及权限数据均不变。

## Evidence boundaries

- PHPUnit Feature 可以证明服务端范围、拒绝行为、排序和重定向，不能证明已部署。
- React 页面不需要新增产品控件；若现有组件行为无需改变，则不以 Vitest 替代服务端授权证据。
- 本地质量门、Git 提交、生产部署和线上只读验证分别报告，不互相替代。
