## Existing behavior and decision
现有 `Reimbursements/Index` 对所有用户都使用“报销审批”标题和审批状态栏。服务端已具备本人/知会/分配审批/管理范围查询、草稿、附件和提交服务，PC 缺少编辑表单。采用新增 PC 表单并分离申请/工作台页面上下文，不复制报销引擎、不新建客户端专用数据表。

## Entry points and capability mapping
| 现有能力/字段 | 新载体和保留方式 |
| --- | --- |
| 共用报销 OA 导航 | `报销申请` 面向原有允许访问报销的账号；`OA 审批` 另限管理员，计工专用账号仍排除 |
| `/reimbursements` 本人/知会清单 | 默认申请人上下文；保留过滤、分页、状态、详情与知会入口 |
| PC 管理员全部/分配审批清单 | `/reimbursements?workspace=approval`，管理员显示审批视图；保留筛选、分页、配置和当前节点操作 |
| 旧 PC 带 all/review 的链接 | 管理员规范化跳转工作台并保留查询条件；普通用户显示申请视图，默认本人范围；底层授权规则保持 |
| JSON index/approvals 路径 | 保留现有移动端响应形状及已授权数据语义，页面展示不改通用查询权限 |
| 新建申请 | `/reimbursements/create`，以现有 submit 权限校验并加载服务端类型与知会人选项 |
| 手工草稿 | 本人草稿列表/详情提供继续编辑，使用现有 UUID、revision 和冲突保护；PC 与小程序共用草稿 |
| 批量 AI 草稿 | 本期保留已有只读和附件能力及移动端继续处理提示，不伪装为免校验手工草稿 |
| 驳回重提 | 当前版本的 owner + can_resubmit 提供编辑入口，保留新版本、历史版本和首节点重启规则 |
| title/type/note/cc | 原字段含义与服务端合法性约束不变，PC 手工编辑 |
| items.description/amount/invoice_date/attachments | 简短费用说明≤20字、金额、可选开票日期、原附件列表；新上传附件可预览、移除或失败重试，无自动识别 |
| submission_key、fingerprint、draft_revision | 复用已有并发/重试契约，重复点击不重复提交，冲突不覆盖别人或另一端的新修改 |
| 原件、zip、通知、审批记录 | 沿用现有详情权限与文件入口，原始 TOS 文件不删除 |

## Access boundaries
申请能力使用现有 `reimbursements.submit`，不向无此权限的角色扩权。工作台展示由服务端提供的管理员角色能力决定。普通用户隐藏审批入口与审批操作；构造 PC 审批视图参数仍返回申请人页面，不新增或修改底层审批接口的权限规则。已有决策 API 的当前节点身份、并发、或签/会签约束继续保留；不因普通用户界面改动而在共享服务重写角色体系或移动端契约。

## Form behavior
手工费用保存到现有草稿服务；新增薄封装 POST /reimbursements/drafts 以支持未上传附件时保存草稿（复用现有 save(create=true)，不改 PUT 契约）；附件上传后只关联，不调用 recognize/evidence start，不将未识别视为错误。保留文件格式/体积/归属、安全、金额和必填项检查。保存、上传、提交各有进行中和失败状态；提交中禁用重复操作。编辑旧版长说明或旧批量来源时不静默截断底层数据：仅可编辑符合本期手工入口条件的草稿，历史重提保留原始附件及来源，需缩短的说明明确交由用户确认修改。

## Alternatives
只改导航文字不能补齐 PC 新建表单，也不能解决直接访问工作台的问题。用户明确要求只隐藏普通用户 OA，因此只调整 PC 页面上下文，不变更共享服务/移动 API 的权限或流程。

## Risks, rollback and evidence
主要风险为普通账号通过旧链接进入审批布局、个人/知会数据被误隐藏、上传引发 AI、草稿冲突丢内容、重复提交。以 Feature 和 UI 测试覆盖对应负向与保留路径。无需数据迁移；代码回退后已有草稿/申请仍可在原移动入口使用。发布须先合并 PR；仅使用专门测试单做在线写入验收，不操作韩艳勇等真实审批。方案校验、代码测试、合并、部署、PC真实登录验收分别报告。
