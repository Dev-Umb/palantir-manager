## Approach
1. 通过现有 RBAC 增量安装出纳角色，复用“查看全部报销”权限。只对出纳开放 OA 查看入口，服务端保持实际审批权与查看权分离；被错误列入节点也不能凭出纳身份处理审批。保留管理员当前节点审批规则以及其他原有角色边界。
2. 复用现有列表/详情、附件授权与报销通知页面；出纳默认打开全部报销并可按状态查询，提供清楚的通知未读提示，不新增付款操作。
3. 在原审批事务确认最终 approved 的位置，以当前有效出纳角色成员补充完成知会，复用原有通知唯一约束和 cc 访问记录；与既有接收人去重。出纳角色收件人在非最终通过事件中不收到报销知会，其余人员不受影响。
4. 完成知会读取当前角色成员，不改已提交单据的流程快照或现有流程全局触发条件。上线前未完成单据后续通过时同样通知；历史结束单据不重发。
5. 使用现有站内报销通知渠道；不扩展微信订阅、短信、邮件或外部消息，不声称已送达用户微信。

## Capability mapping
| 既有能力 | 承载及变化 |
|---|---|
| 管理员 OA 与节点审批 | 原入口与原顺序，保留 |
| 普通用户申请/本人/知会 | 原入口及数据范围，保留 |
| 全部报销查看 | 原 reimbursements.manage 和列表/详情，增加出纳角色 |
| 附件预览下载 | 原版本访问校验，出纳按查看范围访问 |
| 原申请人/知会通知 | 原事件、内容和去重保留；出纳角色只收最终通过事件 |
| 在审历史快照 | 不重写，在其未来最终通过时补充出纳收件人 |
| 出纳账号登录 | 新独立角色账号，落到 OA 查看页 |

## Rollout and rollback
先通过定向及完整质量门禁，PR 合并后发布；备份受影响文件及新增账号/角色授权状态。账号生成临时随机密码，首次登录使用现有改密提示，不复用其他人的密码或微信绑定。只做增量角色与账号配置，不运行业务数据重置，不修改真实审批单进行验收。
回滚代码时同时撤回新增角色授权/停用新账号，保留通知和审计证据，不删除报销数据。线上完整流程验证仅使用明确标注的隔离测试单；已有真实单据只读核验。

## Evidence boundaries
本地测试、质量门禁、PR 合并、部署健康、出纳正常登录验收分别记录。账户创建完成后回读其角色与权限；未完成部署或线上登录前不得声称可用。
