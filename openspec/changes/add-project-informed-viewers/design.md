## Context

业务对象数据存放在 `object_records.payload` JSON 中。项目可见性由 `ProjectVisibility` 统一控制，项目负责人账号存放在 `business_owner_user_id`。当前页面的 `can.update` 是对象级能力，同一页无法区分负责人项目和知会项目，因此新增知会可见性时必须同时增加记录级更新能力，不能只依赖前端隐藏按钮。

## Goals and non-goals

Goals:

- 支持一个项目知会多个业务员。
- 只有项目负责人和管理员能够维护知会人员。
- 被知会业务员只读查看项目，并能明确识别知会来源。
- 后端授权、列表单元格编辑和编辑弹窗保持一致。

Non-goals:

- 不把被知会业务员加入项目负责人、提醒接收人或合同管理员。
- 不赋予被知会业务员合同、客户或联系人额外权限。
- 不新增知会通知、已读回执、转交、评论或协作流程。
- 不改变财务和管理员原有的全项目可见范围。

## Decisions

### JSON 字段与账号类型

项目使用 `informed_business_user_ids` 保存去重后的业务员账号字符串 ID 数组，元数据类型为 `multiaccount`。该类型复用现有多选组件，但在服务端独立验证账号存在且具有 `business` 角色，避免把账号伪装成业务对象关联。

### 可见性与关联对象边界

`ProjectVisibility::scope()` 对业务员返回“本人负责 OR 本人在知会人员数组中”的项目。关联合同等对象仍只使用本人负责项目集合，因此知会不会隐式扩大合同访问范围。

### 记录级写权限

对象级 `can.update` 保留用于说明当前角色是否拥有项目更新能力；格式化后的每条项目记录新增 `can_update`。业务员仅在 `business_owner_user_id` 等于本人时为真，被知会但非负责人的记录为假。后端 `update` 同样执行该记录级判断，防止直接构造请求绕过界面。

### 知会标记

格式化项目记录新增 `is_informed_project`，仅当当前用户是知会人员且不是项目负责人时为真。项目列表在项目名称前显示“知会项目”小标记；负责人、财务和管理员不显示该标记。

## Risks and mitigations

- PostgreSQL 与 SQLite 的 JSON 查询语义可能不同：Feature 测试覆盖 SQLite，现有 Eloquent `whereJsonContains` 生成对应数据库方言；部署前通过生产构建和迁移无变更检查确认。
- 对象级更新权限可能误开知会项目编辑：前后端同时使用记录级能力，并测试直接 PUT 返回 403。
- 删除或停用业务员后历史名称丢失：字段保存账号 ID，显示时实时解析；不存在账号显示为空但不破坏项目记录。

## Migration and rollback

元数据同步会把新字段加入项目定义；既有项目没有该键时按空数组处理，无需数据迁移。回滚时移除元数据字段、知会查询和记录级标记即可，既有 payload 中残留键不会影响旧代码。

## Evidence boundaries

- PHPUnit Feature 证明可见范围、写入校验和后端 403，不能证明浏览器视觉布局。
- Vitest 证明知会标记和编辑入口行为，不能证明服务端授权。
- 本地构建和质量门禁不等于已部署或线上验证。
