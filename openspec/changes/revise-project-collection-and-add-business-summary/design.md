## Context

项目主档 `project.payload` 是本需求唯一的数据事实与编辑来源。独立财务台账已经废弃，本变更不得恢复、暴露或依赖它。当前项目金额归一化会把回款进度按合同额回退并限制在 0–100%；业务概括表和大盘需要直接读取同一项目主档字段，不能形成第二份会漂移的业务数据。

项目数据存储于 `business_objects` 与 `object_records.payload`。通用对象页按 `BusinessObject` 元数据生成导航和列表，`ProjectVisibility` 对管理员、财务、业务员及知会人员实施项目范围约束。当前业务员项目范围以项目的 `business_owner_user_id` 与既有知会规则为准；本变更直接复用该规则，不另行发明授权关系。

## Decisions

### 1. 项目回款进度使用单一严格公式

- 有效分母：可解析、有限且大于 0 的 `occurred_amount`。
- 有效分子：可解析且有限的 `paid_amount`；缺失时沿用现有金额归一化为 0 的行为。
- 公式：`round(paid_amount / occurred_amount * 100, 2)`。
- 项目表展示时保留两位小数并追加 `%`；持久化值继续是数值，不把符号写入 payload。
- 分母缺失、非数值、非有限、为 0 或负数时，持久化镜像使用 `null`，页面显示 `—`。
- 不回退合同金额，不使用 `min(100, ...)`，因此超额回款可以超过 100%。

`unpaid_amount`、`uninvoiced_amount` 和 `payment_status` 不在本次公式重定义范围内，继续使用既有规则。这样避免把一个百分比口径变更扩散为整个财务状态模型重写。

### 2. 总回款比例使用总额之比，不平均项目比例

驾驶舱对已通过 `object.project.view` 与 `ProjectVisibility` 收口的项目主档镜像计算，与大盘项目金额卡使用完全相同的记录集合：

`Σ有效已回款金额 ÷ Σ有效正数已发生金额 × 100%`

- 只有已发生金额为有效正数的项目同时进入分子和分母，避免分子与分母覆盖范围不一致。
- 已回款金额缺失按现有金额语义计为 0；非数值或非有限值视为无效并从该比率覆盖中排除。
- 总分母为 0 时返回 `null`，界面显示 `—` 与“暂无可计算的已发生金额”。
- 返回有效项目数/可见项目总数、已回款分子和已发生分母，供页面显示口径与覆盖。
- 不逐项目封顶，因此总比例也可能超过 100%。

现有 `add-company-operations-cockpit` change 中所有“加权回款率”描述在实施时由本 change 的“总回款比例”要求覆盖；其他 KPI、图表和既有能力映射不受影响。

### 3. 业务概括表采用虚拟只读投影

业务概括表在主数据导航中与客户表、项目主表同层级，但不创建自己的业务记录：

- 元数据定义投影 key、显示名称、七个只读列及来源对象 `project`。
- 列表请求直接查询项目主档，先用 `ProjectVisibility::scope()` 收口，再分页、搜索和排序。
- “客户名称”通过现有 `customer_id` relation label 解析；其他字段直接读取项目 payload/code。
- 展示字段映射：`manager → 负责业务员`、`project_no/code → 项目编号`、`customer_id → 客户名称`、`name/title → 项目名称`、`occurred_amount`、`paid_amount`、`unpaid_amount`。
- 不生成投影 `object_records`，不为投影建立 create/update/delete 权限；所有编辑按钮和批量写能力隐藏。
- 行级“查看/编辑项目”链接跳转既有项目主表记录入口，并由目标路由再次执行项目权限校验。
- 搜索、排序、分页、CSV 导出如对投影开放，必须使用同一项目范围与七列白名单；不得回退到无范围的通用对象查询。

投影入口的可见性直接依赖 `object.project.view`，不以一套可独立授予的 view 权限扩大范围。若实现需要元数据 permission key 以兼容现有导航，该 key 只能作为项目查看权限的从属映射，服务端仍必须二次要求 `object.project.view`。

### 4. 存量重算显式、幂等、可预览

新增面向运维的 Artisan command，复用项目保存路径的同一公式实现：

- 默认 dry-run，列出扫描、预计更新、无需变化、无有效分母与异常数量，不写项目或审计日志。
- 显式 `--execute` 后分批处理并对单项目使用既有事务/锁定同步边界；重复执行不改变已符合新公式的项目。
- 命令只读取项目主档当前的已发生金额和已回款金额，并且只写 `payment_progress`；不得查询或依赖已废弃的独立财务台账。
- 不补造已发生金额，不更新项目的其他字段或其他业务对象。
- 本地测试使用 factory/fixture；生产运行命令需要单独授权、执行前备份与 dry-run 证据。

### 5. 客户联系人仅隐藏独立表，不移除内嵌维护

- 客户联系人继续保留为内部业务对象，既有记录、权限、关联和通用写接口不变。
- 独立导航、对象切换页签、列表路由和 CSV 导出不再暴露客户联系人表。
- 客户表通过单独的联系人元数据 prop 继续打开联系人弹窗；项目主表继续使用既有客户资料同步和联系人关联流程。
- 服务端分别维护“保留对象集合”和“可见表集合”，避免用前端隐藏代替路由边界，也避免误伤内嵌写入。

## Alternatives Considered

### 给业务概括表复制一份记录

拒绝。复制项目字段会引入同步顺序、漂移、重复审计和双入口编辑风险，也违反“编辑依然交给主表完成”。

### 新建数据库 view 或物化表

拒绝。当前需求可以由受限项目查询满足；数据库 view 增加跨 SQLite/PostgreSQL 维护成本，物化表还会产生刷新与一致性问题。

### 只在前端临时拼一个项目表

拒绝。前端隐藏不能代替服务端权限收口，且无法稳定支持分页、搜索、排序和导出。

### 部署时自动执行存量回填

拒绝。生产数据写入需要单独授权与预览证据；实现命令不等于允许在部署流程中静默执行。

### 动态计算项目回款进度而不保存字段

拒绝。项目主档现有契约包含持久化的只读回款进度；本次只替换公式并重算存量，不改变项目主档的数据结构和编辑流程。

## Risks and Mitigations

- `null` 进入旧页面格式化链路可能被显示为 0：增加后端序列化与 React/通用表格测试，明确 `null → —`。
- 投影特殊查询可能绕过通用授权：入口、列表、选中行、导出及跳转分别测试业务员 A/B 隔离和管理员全量。
- 存量重算可能产生大量审计记录或更新时间变化：dry-run 默认开启，显式执行分批处理，并报告实际更新数；只更新值发生变化的项目。
- 当前工作区包含未提交的招投标等改动：实施应在明确基线的隔离 worktree 中进行，或在用户明确指定这些改动为基线后再集成；不得覆盖现有工作区。
- SQLite 测试不能证明 PostgreSQL JSON/UUID 范围查询正确：若投影引入新的 JSON/UUID 查询表达式，必须补 PostgreSQL 路径验证或复用已验证的 `ProjectVisibility` 查询，不以 SQLite 单独作为发布证据。

## Rollback

- 代码回滚恢复旧公式后，不自动把已按新公式重算的项目写回旧值；如确需数据回滚，必须从执行前备份或专门的经批准恢复流程处理。
- 删除业务概括投影入口即可停止展示，不涉及删除投影记录。
- 驾驶舱恢复旧展示只影响只读聚合；不会修改项目数据。

## Evidence Boundaries

- L1/L2 PHPUnit：项目公式、零/缺失/负/无效分母、超额回款、相邻未回款/状态保持、投影权限、字段映射、只读写阻断、存量 dry-run/execute/幂等。
- L3 Vitest：`—`、超过 100%、总回款比例分子分母与覆盖、只读提示、七列、项目入口和无权限不渲染。
- PostgreSQL：仅当新增查询表达式时验证项目范围与 JSON/UUID 类型边界。
- L4 在线：部署与生产回填后另行授权，核对指定业务员只能看到自己的项目、管理员范围、至少一条零分母记录和一条正常比例记录。
