## Why

武全明需要查看全部业务数据，同时只能修改本人名下的数据。现有 admin 角色会放行他人的项目更新，不能通过直接赋予该角色满足需求。

当前工作区为较早的 `codex/optimization-plan`，包含大量未提交改动。本提案参考已核对的业务工作区 `/private/tmp/palantir-finance-project-dates`（`de43e09`）；实施前必须重新确认集成及部署基线。数据库工具当前指向不存在的本地临时 SQLite 文件，尚未确认实际账号 ID、角色及线上状态。

## Scope Contract

- **必须改变**：为武全明增加业务管理查看能力，覆盖当前业务工作区全部业务记录；读取与写入归属判断分开，不能把可见等同于可修改。
- **必须保持**：其他账号与角色权限、现有业务员字段编辑限制、只读合同与经营汇总、创建权限、审计和数据归属；不改变已有数据。
- **允许隐藏**：他人数据上的编辑、删除、关联维护及其他写操作入口；后端同时拒绝越权请求。
- **必须可见**：现有客户、联系人、招投标、项目、经营汇总、合同及其授权业务附件；列表、搜索、详情、现有导出和汇总使用一致的全量范围，并明确呈现只读状态。
- **禁止推断**：不赋予 admin、权限分配、账号管理或修改负责人能力；不开放既有财务专属字段，不恢复已停用模块，不向其他业务员推广该权限。

## What Changes

- 新增“业务管理查看”角色，保留武全明已有业务角色；该新增角色仅补充业务读取权限与全量读取范围。
- 本人项目按 `business_owner_user_id` 判断，不能以创建人或知会人代替负责人。
- 客户、联系人沿用现有业务归属规则，但共享于他人项目的主档不得因本角色被扩大写权限；将共享客户主档作为只读边界，用户已确认。
- 本角色不新增任何写权限；本人记录仍需通过原有对象、字段与操作权限校验。所有他人记录的直接和间接写入入口必须拒绝。
- 核实目标账号的唯一 ID 与现有角色后，再将验证通过的能力赋予该账号，记录角色变更审计。账号 ID 不按姓名硬编码到业务逻辑。

## Capabilities

### New Capabilities

- `business-manager-read-all`: 指定账号查看全部业务数据但仅保留本人数据的既有维护权。

### Modified Capabilities

- 无；不改变其他角色的既有权限契约。

- 不新增持久化字段、依赖、路由或业务数据迁移，复用角色关联与审计。
