## Context

已核对的较新业务模型中，ProjectVisibility::scope 按负责人及知会人筛选业务员可见项目；allowsProjectUpdate 仅允许负责人更新，但 admin 和 finance 可直接通过。客户与联系人通过客户项目归属筛选。通用更新、删除及若干内嵌入口仍使用 allowsRecord，因此只扩大读取范围会连带扩大部分写权限。

## Decisions

1. 将本角色的读取范围与写入归属分离。新增角色补充现有业务对象 view 权限；既有业务角色提供原有写能力，两者不能合成对他人数据的写权限。
2. 对带此角色的账号，写操作先判断本人归属，再判断原有对象权限及字段限制。既有 admin 或 finance 角色若与“只能改本人”冲突，必须在赋权前明确处理，不能用多角色并集绕过归属限制；不得静默删除现有角色。
3. 项目按负责业务员判断；知会、创建、查看、附件访问都不产生所有权。负责人变更后下一次请求必须采用新归属，历史创建人不能继续修改。
4. 客户与联系人没有单独的负责业务员字段。采用已批准的现有本人项目关联及本人创建且未关联项目的规则，再对与他人项目共享的客户主档加只读限制，防止通过本人项目修改他人共用主档。该边界已获用户确认；不创造或迁移所有权数据。
5. 其余记录保持已有归属和操作限制；合同、经营汇总继续只读。没有可证明本人归属的记录不因新增角色获得写权限。
6. 统一审核现有保存、删除、内嵌客户/联系人维护、关联改挂、AI 提案确认及附件写入入口（仅实际存在的写入口），不能只隐藏按钮。新增或更新本人数据时，也不能借关联字段修改他人的项目或主档。
7. 元数据同步必须保留新增角色定义及其 view 权限；取消分配后恢复原业务范围。目标账号操作使用已核实的唯一 ID，记录之前与之后的角色，不重置密码。

## Capability Mapping

| 原有能力 | 本角色的承载与限制 |
| --- | --- |
| 项目列表、搜索、详情、导出 | 沿用原入口，全部项目可读，本人负责项目按原字段权限编辑 |
| 项目内客户、联系人 | 沿用原入口，可读全部，写入另查主档归属及共享边界 |
| 客户与招投标列表 | 沿用原入口，全部可读，原有新建与编辑资格不增加 |
| 合同及业务附件 | 原有查看、下载入口；合同保持只读，附件读取遵循关联记录读取权 |
| 经营汇总和现有业务看板 | 原有入口，读取范围一致；汇总仍无独立编辑记录 |
| 保存、删除、关联维护与 AI 写入 | 原入口，按本人归属及原对象/字段权限双重判断 |
| 系统账号与权限配置 | 不通过本角色授予 |

## Risks and Validation

- 在包含当前业务模型的隔离工作区实施，保留主工作区所有未提交内容。
- L2 验证本人可改、他人可读不可改、知会无写权、创建人与负责人不一致、无归属、共享客户、负责人变更、多角色、角色撤销、字段夹带和关联改挂。越权请求不能写数据或产生成功审计及业务副作用。
- 覆盖列表、搜索、详情、导出、关联选择与附件的读取一致性；测试普通业务员仍只看原范围、管理员和财务保持原行为。
- L3 验证逐行按钮、只读状态、本人编辑与失败反馈。数据库权限子查询需要考虑实际线上数据库类型，SQLite 通过不能当作 PostgreSQL 验证。
- 赋权前确认账号 ID、当前角色和真实集成基线；赋权后核对角色持久化并验证实际用户路径。

## Alternatives

- 直接赋予 admin：拒绝，会允许修改他人项目及管理系统权限。
- 只扩大 scope 或只隐藏编辑按钮：拒绝，现有写入口依赖可见性，存在后端越权。
- 全体业务员全量可见：拒绝，本需求只针对武全明。

## Rollback and Evidence

回滚仅撤销本次新增的目标账号角色关联并恢复本次代码，不删除角色关联之外的数据或改写业务归属。分别报告提案、代码、本地测试、质量门禁、提交、部署、账号赋权及实际用户验证，不将其中任意一项代替另一项。
