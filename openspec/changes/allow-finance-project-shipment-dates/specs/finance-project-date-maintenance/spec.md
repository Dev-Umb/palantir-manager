## ADDED Requirements

### Requirement: 财务可维护项目三项日期

系统 MUST 允许财务通过项目主档既有入口修改首次发货日期、末次发货日期与末次回款日期；页面和服务端 MUST 使用一致的字段权限，且 MUST 沿用项目可见范围与审计。

#### Scenario: 财务保存有效日期

- **WHEN** 财务对授权范围内项目提交三项合法日期
- **THEN** 系统 MUST 保存到现有同名字段，重新读取仍显示提交日期，并沿用现有更新审计

#### Scenario: 财务夹带无权修改的项目字段

- **WHEN** 财务保存日期时夹带项目名称、负责人或系统字段的越权变化
- **THEN** 系统 MUST 按现有越权处理约定拒绝或丢弃无权变化，受保护字段保持不变

### Requirement: 保留相邻角色与项目范围

系统 MUST 保留业务员和管理员对发货日期的既有编辑能力、业务员对末次回款日期的只读限制，以及其他角色和多角色账号的既有权限规则。

#### Scenario: 业务员维护发货日期

- **WHEN** 有项目编辑权的业务员提交合法首末发货日期并夹带末次回款日期变化
- **THEN** 发货日期 MUST 可按既有规则维护，末次回款日期 MUST 保持受保护

#### Scenario: 无权限用户直接请求

- **WHEN** 不具备项目更新权限或不在可见范围内的用户直接请求修改日期
- **THEN** 系统 MUST 拒绝更新，原日期与相邻数据保持不变

#### Scenario: 管理员与多角色账号

- **WHEN** 管理员或同时具有财务与业务角色的账号访问项目编辑入口
- **THEN** 系统 MUST 保留既有角色优先规则，三项日期按该账号最终权限展示与校验，不额外扩大其他字段权限

### Requirement: 日期校验与回款提醒保持一致

三项日期 MUST 遵循既有合法日期及可选空值规则；两项发货日期都有值时末次 MUST 不早于首次。末次回款日期 MUST 保持实际业务日期语义，并遵循既有提醒更新规则。

#### Scenario: 非法格式或首末倒置

- **WHEN** 财务提交非法日期，或提交值与已保存值合并后末次发货日期早于首次
- **THEN** 系统 MUST 返回明确校验错误，不部分保存，不产生成功更新的副作用

#### Scenario: 同日与可选空值

- **WHEN** 首末发货日期相同，或财务按现有规则填写单端日期或清空可选日期
- **THEN** 系统 MUST 接受符合既有校验的值，不增加必填约束或自动推算另一端

#### Scenario: 仅修改发货日期

- **WHEN** 财务仅改变首末发货日期
- **THEN** 系统 MUST 保持原回款提醒起算时间、末次回款日期、财务金额和其他项目字段

#### Scenario: 修改末次回款日期

- **WHEN** 财务实际改变末次回款日期
- **THEN** 系统 MUST 按既有规则更新提醒周期，并保留提交的业务日期，不以系统更新时间替代
