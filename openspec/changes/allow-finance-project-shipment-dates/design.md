## Context

已核对业务分支中的 `BusinessWorkspace::FINANCE_FIELD_KEYS` 包含 `last_payment_date`。财务使用该集合确定可写字段，而业务员通过排除该集合来决定可写字段。因此直接向该集合追加发货日期会剥夺业务员现有权限。

## Decisions

1. 为财务角色的项目可写集合追加 `first_shipment_date`、`last_shipment_date`，不扩大业务员排除集合。保留现有多角色判断优先级。
2. 三项日期仍映射到项目主档既有同名 payload 字段和日期控件。没有新入口、新副本或字段退役。
3. 服务端继续按照实际用户可写字段过滤请求；财务夹带项目名称、负责人、系统字段等变更不能生效。页面只读状态由同一权限来源决定。
4. 在合并已保存值与合法提交值后执行首末日期校验，覆盖只修改一端的情况。沿用现有空值、非法日期处理方式，不新增必填约束。
5. `last_payment_date` 的变更继续触发现有回款提醒规则；发货日期不加入回款变化字段集合。历史日期不被系统更新时间或历史台账覆盖。

### 验证发现的必要边界修正

既有提醒检测使用严格类型比较，JSON 持久化后的整数百分比（例如 `10`）与重算浮点数（`10.0`）被误判为回款变化。为满足仅改发货日期不重置提醒的已批准契约，对既有回款变化检测集合中的金额和百分比字段，有效数值按浮点数比较；日期和状态继续严格比较，真实数值变化与空值变化仍触发提醒更新。合同金额的变更判断同样忽略等值数值类型差异，避免只改日期就把合同金额来源改成手工维护。仅修正这两处保存副作用判断，不改变金额归一化、公式、触发字段集合、同步来源规则或提醒周期。

## Alternatives

- 向财务专属字段集合直接加两项日期：拒绝，会移除业务员既有编辑能力。
- 赋予财务整个项目编辑能力：拒绝，超出字段权限需求。
- 在当前旧工作区新建日期字段：拒绝，新业务基线已有字段，会产生错误的重复实现。

## Risks and Validation

- 实施前确认实际集成基线包含已核对业务模型，在隔离 worktree 中实现，保留当前所有未提交工作。
- L2 覆盖财务三个日期保存、两项发货日期的业务员原有编辑权、末次回款日期业务员只读、管理员、多角色、无权限账号及财务夹带其他字段。
- 日期边界覆盖非法格式、末次早于首次、同日、单端修改与现有清空行为；失败不得部分保存或写入成功审计。
- 提醒边界覆盖只改发货日期不重置提醒、实际改变末次回款日期遵循原有提醒行为；金额与项目其他字段保持不变。
- 页面检查三项日期的权限元数据与控件可编辑性、错误反馈、保存后重新读取和失败后的显示；若修改 UI，补 L3 回归。

## Rollback and Evidence

回滚仅恢复财务两项发货日期的旧编辑权限，保留已保存日期，不执行历史数据重写。本地测试、质量门禁、提交、部署与线上验证分别报告。
