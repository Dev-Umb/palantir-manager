## Representation and validation

沿用 first_shipment_date 字符串，允许四位YYYY或有效YYYY-MM-DD；年份合法范围1000至9999。用户输入的“2016年”在入口规范为“2016”。不新增影子日期，也不把年转换为某一天存储。完整日期和空值含义保持。

仅项目首次发货字段携带允许年份的元数据，不能仅凭type=date开放全部日期。服务端不能信任客户端提交的元数据。

## Capability mapping

| 现有能力/字段 | 新载体/入口 | 保留验证 |
|---|---|---|
| 首次发货日期完整值/清空 | 原payload字段与编辑入口 | 完整日期原样保存；空值不变 |
| PC表单和表格内联编辑 | FieldControl及ObjectGrid既有入口 | 选择精度；年份输入不得输入一位就自动提交 |
| 列表、详情及导出 | 原展示/导出字段 | 显示月日不详，导出四位年份，不产生Excel完整日期 |
| 服务端日期筛选/排序 | 原查询入口，字段专用精度语义 | 其他日期查询保持 |
| Flutter项目编辑和筛选 | mobile/lib/projects.dart、list_filters.dart | 保存再编辑不丢年份；旧完整日期保持 |
| 财务和业务员写权限 | BusinessWorkspace现有白名单 | 不扩大或剥夺任何角色能力 |
| 首末顺序校验 | 原服务端guard，首次允许区间 | 仅确定末次早于首次时拒绝 |
| 合同及末次回款日期 | 原控件和校验 | 仍拒绝纯年份，提醒规则不变 |

补充消费者核对：移动网页复用 React 编辑入口；微信小程序 edit.wxml 为该元数据字段提供纯年份文本输入及完整日期选择，services/business.js 的详情行使用服务端 display；CSV 导出沿用原 payload 并保留四位年份。BuildAiUpdateProposal 仅允许 customer 和 customer_contact，项目日期不在 AI 可写范围，本次不扩大权限。

## Comparison semantics

年份作为未知日的全年区间参与比较，但区间边界仅用于比较，不写入或显示为实际日期。若末次日期早于首次年份的开始，拒绝；同年末次日期允许，因为实际首次月日未知。完整日期维持旧校验。

首次日期筛选：等于YYYY匹配该年纯年份和完整日期；等于具体日期只匹配该完整日期。before/after为整个可能区间确定在阈值之前/之后；between按整个区间被包含判断，不将未知月日归入某个月。UI需说明仅年份记录在精确区间查询中的含义。空值查询不变。排序采用区间下界并以原值作稳定次序，不声称纯年份发生在1月1日。

## Rollout and rollback

先测试与质量门禁，再PR合并及部署，验证PC及实际移动端消费者能保留纯年份后再写9条数据。回填只改为空的首次日期，源行49/50/51/52/53为2016，58为2021，59/64/66为2022；遇到已存在完整日期则暂停该条，不降低精度。

写入前保存字段级备份、并发旧值保护和审计。代码回滚前先恢复本批年份字段，避免旧date控件吞掉年份；保留备份、源表和附件。
