## Context

Palantir Manager 通过 `config/xyc.php` 定义业务对象，业务记录保存在 `object_records`。当前 `contract` 已通过 `project_id` 与 `project` 建立一对多关系，合同创建、更新、删除会触发项目合同编号/数量汇总、合同金额与流程联动以及合同提醒。项目主档中的 `related_contract_no`、`contract_qty`、`contract_amount` 是派生结果，不是合同明细的第二份可写副本。

现有通用项目表支持列表内联编辑、弹窗新建/编辑/详情；file/files 字段通过 multipart 上传，但文件不能在 AG Grid 单元格中直接编辑。最新主线合同已经提供加工函、合同、对账单三类可累加多附件，且附件会约束合同状态推进。Laravel 13 支持嵌套数组逐项校验；Inertia v3 对包含文件的更新应使用 multipart `POST` 并通过 `_method=PUT` 模拟更新。

## Scope contract

- 必须改变：项目主档成为合同明细及附件的唯一人工写入口；一个项目支持多份合同；项目保存同步合同新增、修改和显式删除；合同表改为全局只读。
- 必须保持：合同一对多基数、现有合同编号、全部既有合同字段、加工函/合同/对账单三类多附件及追加语义、附件驱动的状态校验、客户与项目一致性、金额/数量/状态汇总、项目流程、提醒、审计、附件授权、合同列表/查询/详情/导出、项目权限与可见范围。
- 允许隐藏：合同表的新建、编辑、删除按钮、单元格编辑能力及对应写入口。
- 必须可见：项目详情中的全部合同明细及附件；项目编辑中的已有合同、同步错误和逐条删除意图；合同表中的最新同步结果。
- 禁止推断：不合并多份合同，不重编号历史合同，不把合同明细复制进项目 payload，不改变财务口径，不改变客户—项目关系，不扩大非业务角色的合同写权限，不清理无关附件。

## Goals and non-goals

Goals:

- 业务人员在一个项目上下文内完成项目资料和多份合同资料维护。
- 项目与合同记录同步失败时不留下部分数据库写入。
- 现有合同数据无需迁移即可在项目界面继续维护。
- 合同表仍可承担跨项目台账查询与导出，但不会形成第二写入口。

Non-goals:

- 不新增独立合同物理表或改变 `object_records` 存储模型。
- 不支持在项目表格单元格内直接选择文件；附件在项目新建/编辑弹窗内维护。
- 不引入合同审批、版本管理、电子签名、OCR 或合同解析；现有三类多文件附件集合原样保留。
- 不改变回款、开票、应收等财务对象的维护入口和计算口径。
- 不自动删除未被本次合同替换或显式删除所涉及的存储文件。

## Decisions

### 1. 只迁移写入口，不复制合同数据

`contract` 记录继续是合同明细的唯一持久化载体。项目响应增加派生属性 `contracts`，由 `contract.payload.project_id = project.id` 的授权记录实时装配；`project.payload` 只保留现有汇总字段，不增加 `contracts` JSON。

这样既满足“项目主表维护、合同表同步展示”，又避免项目 payload 与合同记录两份数据漂移。既有合同天然出现在对应项目下，不需要批量迁移。

### 2. 项目表单使用稳定 ID 同步一对多合同

项目表单提交：

- `contracts` 是合同明细数组；已有明细必须携带服务端返回的合同记录 `id`，新明细没有 `id`。
- `deleted_contract_ids` 只包含用户在界面明确确认删除的已有合同 ID；数组中暂时缺失但未列入删除集合的记录不得被服务端推断删除。
- `customer_id`、`project_id`、合同系统 `code/contract_no` 由父项目与服务端生成，客户端不能覆盖。
- 可编辑字段为现有 `status`、`ctype`、`amount`、`signed_date`、`contract_chase_record`、`contract_qty`、`remark`，以及现有 `processing_letter_attachments`、`contract_attachments`、`statement_attachments` 三类多附件。
- 既有附件始终保留；选择新文件表示追加到对应类别而非替换。状态为“已有加工函”时至少有一份加工函附件，状态为“已签署”时至少有一份合同附件；这些现有规则不得绕过。

同步算法在项目创建或更新的数据库事务内：锁定项目、合同对象及该项目现有合同集合；验证提交的已有 ID 全部属于当前项目且用户可写当前项目；先更新和创建，再处理明确删除；最后对受影响项目只执行一次汇总、流程、提醒刷新。任一验证或数据库写入失败时整批回滚。

项目创建时先创建项目记录并取得 ID，再在同一事务内创建合同。项目更新继续保留现有项目 payload 合并、客户变更保护和联系人清理行为。

### 3. 复用合同领域副作用，避免两条规则漂移

新增 `SyncProjectContracts` Action 负责协调合同集合，但不重新定义合同规则：

- 新记录沿用 `CreateObjectRecord` 的编号、标题、关系快照与审计约定。
- 更新/删除抽取或复用现有合同更新所调用的规范化、客户一致性、审计和引用保护逻辑。
- 批次结束复用 `SyncProjectContractAmount`、项目合同财务/流程同步及 `SyncProjectNotifications`。

为避免每条明细重复汇总和递归触发，合同低层写入与批次后副作用需要明确分层；项目来源同步不能调用公开合同 HTTP 路由，也不受合同对象 `read_only` 的界面限制。

### 4. 合同表保留读取能力并在服务端封死直接写

合同对象仍对现有 `business` 和管理员可见，字段、搜索、详情、附件下载与导出保持。`BusinessWorkspace` 对合同返回空可写字段并禁止删除，控制器禁止合同创建，使通用页面不展示新增/编辑/删除和内联编辑。合同元数据不设置 `read_only`，因为现有元数据同步会据此删除对象权限键，违反本变更的公共契约保留要求。

公开合同新增、更新、删除请求必须返回 403，即使调用者是管理员或仍持有历史 `object.contract.create/update/delete` 权限。保留权限键可避免修改角色/权限公共契约；项目合同写入只允许管理员或能够维护当前项目业务字段的负责业务员，财务及项目只读用户不得写合同。

### 5. 项目弹窗承载合同编辑器

- 项目新建/编辑弹窗在既有项目字段下方增加“合同明细”区域，可新增多行、展开编辑、向三类附件分别追加多个文件，并对已有行执行二次确认删除。
- 项目详情弹窗只读展示每份合同的系统编号、业务字段和附件链接。
- 项目表格既有字段内联编辑保持不变；合同集合不增加为 AG Grid 可编辑列，避免文件上传与一对多行在单元格协议中失真。
- 含附件的创建使用 multipart POST；更新使用 multipart POST 加 `_method=PUT`。后端错误键保留 `contracts.{index}.{field}`，前端定位到对应合同明细。

## Validation and authorization

- `contracts`、`deleted_contract_ids` 必须是有界数组；每个已有合同 ID 唯一且属于当前项目。
- 每份合同的字段、状态凭证和 files 规则与现有 contract 定义一致；三类附件复用现有文件类型、单文件大小及数量约束。
- 项目客户是合同客户的唯一来源；不得通过嵌套输入跨客户写入。
- 只有管理员或能够维护当前项目业务字段且通过 `ProjectVisibility` 的负责业务员能同步合同；财务及其他只读项目用户只能查看其有权查看项目下的合同。
- 直接合同 CRUD 始终拒绝；附件下载继续走现有授权控制，不能暴露存储路径为公共文件。

## Risks

- 文件存储不参与数据库事务，数据库回滚可能留下本次新上传但未引用的孤儿文件：同步 Action 应记录本次新存路径并在异常时清理，不能删除旧附件。
- 项目保存与旧合同直写并发可能覆盖：合同表改只读后只剩项目入口；事务内行锁和 ID 归属校验封闭并发窗口。
- 当前工作区已有覆盖核心文件的未提交改动：实施时必须在现有改动之上做最小补丁并逐文件复核，不能重置或覆盖用户工作。
- 合同批量副作用若逐条触发会重复审计外的汇总/提醒：设计要求逐条合同审计、批次一次项目级刷新。

## Rollback

- 回退项目合同编辑器、项目请求扩展与 `SyncProjectContracts`，恢复 `BusinessWorkspace` 和控制器中的合同写能力，即可回到独立合同表维护。
- `attachment` 字段回退前不得删除已上传文件或 payload 值；若字段暂时不展示，数据仍保留，可在再次启用时恢复。
- 本变更不新增物理表或批量迁移，因此不需要数据库结构回滚和历史合同反迁移。

## Evidence boundaries

- L2 PHPUnit：项目创建含多份合同与附件；项目更新新增/修改/明确删除；未提交删除意图时保留；合同 ID 越权/跨项目/跨客户拒绝；批次失败数据库回滚；项目权限与 `ProjectVisibility`；直接合同 CRUD 403；合同列表、详情、导出和附件授权保持。
- L2 相邻断言：既有合同编号/数量/金额汇总、项目流程/提醒、项目普通字段内联更新、客户变更保护与非合同财务对象保持。
- L3 Vitest：多合同增删编辑、三类历史附件保留与新附件追加、新附件 multipart、更新方法伪装、明细错误定位、只读合同页无写控件、项目只读详情展示。
- 构建与门禁：focused PHPUnit/Vitest → `vendor/bin/pint --dirty --format agent` → `npm run build` → `composer quality:gate`。
