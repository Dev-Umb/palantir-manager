## Context

customer、customer_contact 和 project 都存储在 `object_records`，项目通过 `customer_id` 与 `customer_contact_ids` 关联主档。现有 `ProjectCustomerManager` 使用独立 JSON 请求提前保存客户或联系人，项目随后再次保存关系，存在跨请求部分成功窗口。

## Scope Contract

- 必须改变：客户资料与联系人在项目表单平铺；点击项目保存一次完成全部写入。
- 必须保持：既有记录、项目多联系人、客户可见隔离、财务和招投标权限、客户备注与其他客户字段。
- 允许隐藏：项目内“新增客户”“维护当前客户”弹窗及联系人脱焦保存提示。
- 必须可见：客户匹配结果、客户字段冲突、覆盖确认和服务端错误。
- 禁止推断：不按名称单独合并、不删除移除联系人、不修改客户备注、不把规则扩展到招投标保存。

## Data Contract

项目请求在 `payload.customer_profile` 携带临时输入：

```json
{
  "customer_id": "optional uuid",
  "name": "客户名称",
  "address": "客户地址",
  "level": "A|B|C|empty",
  "customer_nature": "国央企|私企|empty",
  "overwrite_confirmed": false,
  "contacts": [
    {"id": "optional uuid", "name": "联系人姓名", "phone": "手机号"}
  ]
}
```

该结构只用于请求，不持久化到 project payload。服务端解析后写入真正的 `customer_id` 和 `customer_contact_ids`。

## Matching and Conflict Rules

- 所有标识字段保存前去除首尾空格，空地址和空手机号作为空字符串参与组合匹配。
- 未显式选择客户时，全局按名称和地址组合匹配；没有匹配则创建。
- 显式选择客户后允许修正名称或地址；若新组合属于另一客户，则改为关联该已存在客户，不删除原客户。
- 匹配客户的地址、等级或性质与提交值不同即形成逐字段冲突；未确认覆盖时不得保存。
- 联系人在已解析客户内按姓名和手机号组合匹配。显式选择的联系人可被更新；若新组合已存在则复用已有联系人。
- 从项目移除联系人只从 `customer_contact_ids` 删除引用，客户联系人记录保持不变。

## Save Flow

1. 前端在项目提交前调用只读预检接口。
2. 无冲突时继续提交；有冲突时展示当前值与新值并等待用户选择。
3. 用户拒绝时保留表单且不发起项目保存。
4. 用户确认后提交 `overwrite_confirmed=true`。
5. 服务端在引用图锁和单一事务中解析/锁定客户，创建或更新联系人，再保存项目。
6. 任一步验证或写入失败时整笔回滚。

实际保存仍再次校验冲突，预检不作为授权或一致性保证。

## UI

- 项目通用字段中隐藏原 `customer_id`、`customer_contact_ids` 与客户 lookup 编辑控件，改由一个平铺区承载。
- 客户名称输入框提供按权限检索的下拉结果，候选显示名称与地址。
- 等级和性质使用固定下拉；地址直接输入；客户备注不展示。
- 联系人先选择该客户已有记录，再在平铺行中编辑姓名和手机号；可增加空白行。
- 冲突确认使用应用内模态框，不使用浏览器原生 `confirm`。

## Permissions

- 仅管理员和业务员获得平铺客户编辑能力。
- 财务保持既有项目财务字段权限，不因本变更获得客户或联系人写权限。
- 冲突预检和实际同步都执行既有角色及记录可见性校验。

## Rollback

回退前端平铺组件、预检路由、同步 Action、项目保存接入和派生字段；底层客户、联系人、项目数据无需回滚或删除。
