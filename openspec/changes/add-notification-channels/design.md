## Context

项目通知与 tender 通知分别存储，站内记录是业务事实。外部渠道具有网络失败、限流、凭据与隐私风险，因此必须与业务事务解耦。

## Scope contract

- 必须改变：新增统一渠道契约、类型路由、用户偏好、异步投递与可观测日志。
- 必须保持：站内通知先落库；既有通知生成条件、接收人、页面、已读状态和业务事务不受外部失败影响。
- 允许隐藏：未启用的渠道不出现在用户操作路径中。
- 必须可见：投递状态、尝试次数和最终错误对管理员可查询。
- 禁止推断：短信供应商、飞书应用模式、凭据、生产启用策略均等待单独批准。

## Decisions

- `NotificationChannel` 提供渠道 key 与投递方法；调度器按提醒类型及用户偏好解析目标。
- 外发由队列任务执行，最多重试 3 次；业务事务只负责站内通知与提交后派发。
- 默认不启用任何真实外部渠道；日志渠道用于开发验证。
- 项目通知和 tender 通知保留独立数据表，以来源类型与来源 id 关联投递日志。

## Risks

- 重试可能导致供应商重复投递，需要稳定幂等键。
- 用户联系方式属于敏感数据，需要限制读取、日志脱敏与明确保留策略。
- 多实例队列可能并发消费，需要数据库唯一键或原子状态迁移。

## Evidence boundaries

- L1：渠道路由、偏好回退、幂等键。
- L2：事务提交后派发、失败重试、最终状态、站内通知不回滚。
- 不包含真实生产凭据或线上投递验证。
